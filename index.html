システム障害の現実

Why Payment Systems Fail Silently

Financial transaction software must remain correct even when clients retry requests, workers crash, and network connections drop.

[NETWORK]

Lost Webhooks (70% Loss Simulation)

A payment succeeds at the provider, but the confirmation webhook never arrives over the internet. Without reconciliation, customers are charged but never receive products.

[IDEMPOTENCY]

Double-Click Duplicate Requests

Users double-click the checkout button or mobile devices resend dropped HTTP packets. Without idempotency keys and request hashes, users get charged twice.

[CONCURRENCY]

Race Conditions & Concurrency

Two webhook callbacks or refund requests arrive at the same millisecond. Without row-level database locks, race conditions corrupt balances and double-fulfill orders.

[AUDIT]

Ghost Payments & Abandonment

Transactions get stuck in PENDING status indefinitely. Background reconciliation sweeper discovers abandoned checkouts and cleans up state using the provider truth-source.

[RETRY]

Gateway 504 Timeouts

External gateway call drops mid-flight. SakuraPay wraps gateway intent generation in database transactions so timeouts trigger clean atomic rollbacks.

[SECURITY]

Amount Tampering (1-Cent Flaw)

Malicious actors spoof webhooks capturing $0.01 for a $150 item. Zero-trust validation rejects mismatched amounts before any state changes can occur.

実装パターン

Engineering Patterns in Code

Concrete mechanisms implemented in the repository to guarantee transaction correctness.

Core

Database-Backed Idempotency

Combines client-provided keys and SHA-256 payload hashing with PostgreSQL ON CONFLICT (idempotency_key). Duplicate requests return cached responses with zero duplicate row creation.

Core

Row-Level Locking

Uses SELECT ... FOR UPDATE OF p to lock the payment row before state evaluation. Serializes parallel webhook delivery and eliminates race condition corruption.

Core

Canonical Winner Selection

The first successful payment transaction updates the order to PAID. Any subsequent successful payment is quarantined as DUPLICATE_SUCCESS and funneled into auto-refunds.

Safety

Hit-and-Run Pooling

Background workers use FOR UPDATE SKIP LOCKED to claim work batches, transition state, and release the database connection before making HTTP network calls.

Chaos

Lossy Network Simulation

A built-in chaos engine simulates a 70% internet webhook drop rate and random gateway 504 timeouts to rigorously test asynchronous recovery pipelines.

Safety

Two-Phase Reconciliation

Automated sweeper queries provider truth-sources to recover payments abandoned by lost webhooks (>24h) and escalates permanently stalled refunds (>72h).

Core

Integer Minor Unit Currency

Monetary values are modeled strictly as BIGINT integer units (e.g. paise / cents), preventing IEEE-754 floating-point rounding vulnerabilities.

Safety

Zero-Trust Amount Verification

Webhook handlers compare captured amounts against parent order intents. Any mismatch locks the payment into FAILED and aborts processing immediately.

アーキテクチャの意思決定

Architectural Decision Records (ADRs)

Engineering trade-offs and rationale behind the system design.

ADR-001 • Architecture

Why a Modular Monolith?

Starting with microservices adds distributed transaction complexity (2PC/Sagas) before basic financial invariants are proven. A modular monolith provides ACID guarantees across orders, payments, and refunds while preserving modular boundaries for future extraction.

ADR-002 • Persistence

Why PostgreSQL for Concurrency?

PostgreSQL provides robust row-level locking (FOR UPDATE, SKIP LOCKED), strict unique constraints, and ACID transactions. In-memory locks (e.g. Python threading mutexes) fail immediately across multiple Uvicorn worker processes.

ADR-003 • Data Modeling

Why Integer Minor Units?

Floating-point numbers cannot accurately represent currency due to base-2 binary approximation errors (e.g. 0.1 + 0.2 = 0.30000000000000004). Using BIGINT paise/cents completely eliminates mathematical discrepancy.

ADR-004 • Financial Correctness

Why Immutable Records & Compensating Reversals?

Financial records must maintain an untampered audit trail. Never UPDATE historical transaction amounts; instead, create compensating transactions (refund records) to balance accounts.

ADR-005 • Reliability

Why At-Least-Once Delivery Semantics?

Over distributed networks, exactly-once delivery is physically impossible under network partitions (Two Generals Problem). Webhooks are designed for at-least-once delivery, requiring the receiver to deduplicate using event IDs.

ADR-006 • Operations

Why Independent Reconciliation?

Online transaction processing (OLTP) optimizes for latency. Reconciliation audits truth-sources offline on scheduled intervals without contending for locks on active checkout operations.

1. Idempotent Upsert with Insertion Detection
SQL (PostgreSQL) 
INSERT INTO orders (idempotency_key, request_hash, amount, created_at)
VALUES ($1, $2, $3, $4)
ON CONFLICT (idempotency_key)
DO UPDATE SET idempotency_key = orders.idempotency_key
RETURNING order_id, amount, status, idempotency_key, provider_order_id, created_at,
          (xmax = 0) AS inserted;
-- xmax = 0 evaluates to True ONLY if a new physical row was inserted.
-- If conflicting, xmax != 0, enabling the API to distinguish new vs replayed orders.

async with conn.transaction():

3. Hit-and-Run Batch Claiming in Refund Daemon
Python & SQL 
async def claim_batch(pool: asyncpg.Pool, batch_size: int = 50):
    -- Atomically transition rows to 'PROCESSING' and DROP the database connection!
    async with pool.acquire() as conn:
        async with conn.transaction():
            records = await conn.fetch("""
                UPDATE refunds SET status = 'PROCESSING'
                WHERE refund_id IN (
                    SELECT refund_id FROM refunds 
                    WHERE status = 'PENDING_CONFIRMATION' 
                    LIMIT $1 FOR UPDATE SKIP LOCKED
                ) RETURNING refund_id, payment_id;
            """, batch_size)
    -- DB connection is closed here; HTTP network calls to gateway happen lock-free!
    return [dict(r) for r in records]

Core Engineering Methods & Invariants

Formal concurrency, transactional integrity, and reliable delivery mechanisms implemented in SakuraPay.

PostgreSQL · SELECT FOR UPDATE

Pessimistic Concurrency & Row Serialization

PostgreSQL row-level exclusive locking (SELECT ... FOR UPDATE) serializes concurrent mutations on payment intents. When concurrent workers attempt parallel capture and refund operations, row locks serialize access at the database kernel level.

Enforced Invariants:
  • Exclusive row acquisition before balance evaluation
  • Zero race conditions on concurrent over-refund attempts
  • Deterministic canonical winner election
Double-Entry · Balanced Zero-Sum

Double-Entry Ledger & Algebraic Invariance

Every fund transfer posts balanced debits and credits across immutable ledger entries. Historical records are append-only. Corrections and full/partial refunds require compensating journal entries, never destructive row mutation.

Enforced Invariants:
  • Algebraic zero-sum rule: ∑ amount_delta = 0 for all transactions
  • Zero UPDATE or DELETE permissions on historical records
  • Reconstructed balance equals current materialized account state
Dual-Write Hazard Elimination

Transactional Outbox Pattern

Domain state transitions and outbound webhook notifications are committed within the same atomic database transaction (outbox_events). A dedicated worker polls pending events, eliminating dual-write hazards between database commits and network HTTP calls.

Enforced Invariants:
  • Zero lost webhooks on process crash or restart
  • Atomic linkage between payment status and event records
  • Decoupled gateway latency from checkout response time
IETF Draft · SHA-256 Fingerprint

Deterministic Idempotency Key Engine

Client requests supply an Idempotency-Key header and SHA-256 payload digest. On retries with identical keys, the engine serves cached 200/201 responses without re-executing logic. Reusing a key with mismatched parameters rejects with 409 Conflict.

Enforced Invariants:
  • Exactly-once execution semantics under network retries
  • Cryptographic fingerprint prevents parameter tampering
  • Atomic insertion lock guarantees zero duplicate records
RFC 2104 · FIPS 198-1 · Full Jitter

HMAC-SHA256 Signatures & Jittered Backoff

Webhook payloads are signed using symmetric HMAC-SHA256 secret keys passed in the X-SakuraPay-Signature header. Retries employ exponential backoff with full randomized jitter to eliminate thundering-herd spikes on merchant endpoints.

Enforced Invariants:
  • Cryptographic payload authenticity and integrity verification
  • Exponential backoff prevents downstream endpoint overload
  • Dead-letter classification on terminal delivery failure
Read-Only Auditor · Invariant Sweep

Offline Financial Reconciliation Sweeps

An isolated scheduled audit process sweeps PostgreSQL state to mathematically audit integrity rules: verified zero ledger discrepancy (∑ = 0), currency parity, refund-to-capture ceiling compliance, and materialized balance identity—without taking locks on live checkout operations.

Enforced Invariants:
  • Zero lock contention with online OLTP transactions
  • Read-only non-mutating audit guarantees audit trail purity
  • Immediate detection and alerting on financial discrepancy

学術論文と業界標準仕様

Research Papers & Formal References

Foundational computer science research, RFC standards, and literature cited in the architecture of SakuraPay.

REF-01

Life beyond Distributed Transactions: An Apostate's Opinion

Pat Helland (2016) · ACM Queue, Vol. 14 / CIDR

Demonstrates why distributed transactions across independent boundaries fail at scale. Proves that reliable distributed systems must rely on entity-scoped atomic transactions, idempotency keys, and at-least-once messaging with receiver-side deduplication.

SakuraPay Implementation: Direct theoretical basis for SakuraPay's modular entity boundaries, avoiding distributed Sagas/2PC in favor of localized PostgreSQL ACID transactions and outbox idempotency.
REF-02

Transaction Processing: Concepts and Techniques

Jim Gray & Andreas Reuter (1993) · Morgan Kaufmann

The seminal text establishing formal transaction processing foundations: ACID guarantees, isolation levels, serializability, Write-Ahead Logging (WAL), and compensating transactions for non-undoable real-world side effects.

SakuraPay Implementation: Establishes SakuraPay's row-level lock serialization (SELECT FOR UPDATE) and compensating ledger transactions instead of destructive row deletion.
REF-03

Designing Data-Intensive Applications

Martin Kleppmann (2017) · O'Reilly Media (Ch. 7 & 11)

Rigorous analysis of concurrency anomalies, the dual-write hazard between databases and message queues, linearizability vs. serializability, and state machine replication.

SakuraPay Implementation: Direct architectural blueprint for SakuraPay's Transactional Outbox pattern and atomic event state dispatching.
REF-04

The Idempotency-Key HTTP Header Field

IETF HTTPAPI Working Group (2023) · Internet-Draft

Formal specification standardizing the client-provided Idempotency-Key HTTP header to prevent duplicate execution of mutating REST requests under network timeouts and connection drops.

SakuraPay Implementation: Standard-compliant implementation of the Idempotency-Key header, SHA-256 request payload validation, and 409 Conflict handling.
REF-05

Some Constraints and Trade-offs in the Design of Network Communications

H. Akkoyunlu, K. Ekanadham, & R. Huber (1975) · ACM SOSP

Formulates the foundational Two Generals Problem, mathematically proving that two entities communicating over an unreliable network cannot reach guaranteed common agreement with a bounded number of messages.

SakuraPay Implementation: Theoretical basis for rejecting naive exactly-once transport over HTTP and designing SakuraPay webhooks around at-least-once delivery with receiver deduplication.
REF-06

Summa de arithmetica, geometria, proportioni et proportionalita

Fra Luca Pacioli (1494) · Venice, Italy

The earliest published mathematical treatise on double-entry bookkeeping (the Venetian method), introducing the fundamental identity that debits must equal credits for every financial transaction.

SakuraPay Implementation: SakuraPay's ledger structure strictly enforces Pacioli's invariance: every monetary motion creates balanced debit/credit entries with net zero delta (∑ Δ = 0).
REF-07

The Keyed-Hash Message Authentication Code (HMAC)

NIST FIPS PUB 198-1 & IETF RFC 2104 (2002 / 1997)

Cryptographic standard specifying message authentication mechanisms utilizing cryptographic hash functions (such as SHA-256) combined with a secret shared key to guarantee message integrity and authenticity.

SakuraPay Implementation: Applied in SakuraPay's webhook delivery pipeline (X-SakuraPay-Signature), allowing merchants to cryptographically verify payload integrity and authenticity.

デプロイメント構成

Docker Compose Topology

Three isolated containers running in decoupled crash domains sharing one PostgreSQL instance.

[CONCURRENCY]

API Node Container

Serves the REST API and landing page on port 8000 using 4 Uvicorn worker processes.

uvicorn app.main:app --workers 4
[WORKER]

Refund Daemon Container

Continuous worker polling every 3s to safely process pending gateway refunds via atomic batch locks.

python -m app.workers.refund_worker
[RECON]

Reconciliation Sweeper

Scheduled cron worker checking provider truth sources to recover lost webhooks and abandoned orders.

python -m app.workers.reconciliation_worker
